# 05 · 踩坑记录

都是实际踩过的，按痛苦程度排序。

## 1. 工具的 HTTP API 在大群上极慢

**症状**：某些几万条消息的群，每 200 条要 60–90 秒；全量导出要几小时。
**原因**：服务端按会话做了重活（推测是成员名解析/全表扫描），与消息条数不成正比。
**解法**：直读解密后的 SQLite（`wx_export_db.py`）。同样数据量几十秒。

## 2. 同名 cursor 嵌套执行会截断外层迭代

**症状**：遍历"所有 Msg 表"时只处理了 4 张就停了。
**原因**：
```python
for (t,) in cur.execute("SELECT name FROM sqlite_master ..."):
    n = cur.execute("SELECT COUNT(*) FROM [%s]" % t)   # ← 复用了同一个 cursor
```
内层 `execute` 把外层结果集重置了。
**解法**：先 `fetchall()` 或另开 cursor。

## 3. zstd 帧没有 content size

**症状**：`zstandard.ZstdDecompressor().decompress(blob)` 对部分行抛异常。
**解法**：
```python
try:
    s = dctx.decompress(b).decode("utf-8", "replace")
except Exception:
    s = dctx.decompressobj().decompress(b).decode("utf-8", "replace")
```

## 4. message_content 有时是 str 有时是 bytes

```python
if isinstance(b, str):
    return b          # 已经是明文
if b[:4] == b"\x28\xb5\x2f\xfd":
    ...decompress...
return bytes(b).decode("utf-8", "replace")
```

## 5. 一对一聊天里的发送者判断

群里靠 `content` 前缀判发送者；**一对一没有前缀**，只能靠
`real_sender_id → Name2Id → username` 与会话 username 比较：
相等 = 对方，否则 = 自己。比硬编码自己的 wxid 更稳。

## 6. 语音时长字段不可靠

`media_info.duration` 经常是错的（有时是原始长度），应以消息 XML 里的
`voicelength`（毫秒）为准。

## 7. 消息顺序

工具 API 返回的顺序是「新块在前、块内升序」，直接拼接会乱。
一律按 `(create_time, local_id)` 重新升序排列。

## 8. ffmpeg 不能解 SILK

SILK→WAV 必须走工具的 `/api/voice` 或自编解码器。

## 9. Edge headless 打印互相抢端口

**症状**：批量转 PDF 时第一个成功，后面全卡住。
**原因**：固定 `--user-data-dir` + 固定 `--remote-debugging-port`，新实例被旧实例接管。
**解法**：每次用独立 user-data-dir + 随机空闲端口（`html2pdf_safe.py`）。

## 10. 同步盘会瞬时锁住刚写入的文件

**症状**：`PermissionError` / `ReplaceFileW ... EIO`，尤其是批量写文件时。
**解法**：写文件加重试（指数退避），或先写临时目录再移动。

## 11. CSV 字段过大

`csv.field_size_limit()` 默认 128KB，遇到超长消息会报
`field larger than field limit`。开头调大即可。

## 12. 中文 docstring 里的 Windows 路径

```python
"""用法： python x.py --backup C:\Users\me\data"""   # ← \U 触发 unicodeescape 报错
```
把 docstring 改成 `r"""..."""` 或把反斜杠转义。
